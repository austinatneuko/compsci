Definitions

Git
A program that records a history of snapshots you chose.
GitHub
A company that hosts Git repositories and adds a website.
repository
A folder whose history Git is recording, stored in a hidden .git.
commit
A snapshot you chose, with a message and a parent.
staging area
The exact changes marked for the next commit.
branch
A movable name that points at a commit.
working tree
The files on disk right now, which may differ from the last commit.

Diagram

working tree   files you see and edit
      |
      | git add
      v
staging area   the next snapshot, chosen
      |
      | git commit
      v
history        commits on a branch

status tells you which layer you are looking at. Ask it before you ask me.

Git is not GitHub

GitHub is a company that hosts Git repositories and adds a website. Git is a program that records a history of your project as a sequence of commits you chose to make.

If you only ever click upload, you have a backup with extra steps. If you can commit locally, read a diff, and say what changed, you have an instrument.

Do this now

git --version

A version line. If the shell says command not found, install Git for macOS first, then run this again.

Init, status, add, commit

A repository is a folder with a hidden .git that stores history. git init creates it. After that, every file is in a state you must be able to name. Untracked: Git does not know it. Modified: Git knew an older version. Staged: you marked these exact changes for the next snapshot. Committed: in history.

git status is the map. People who skip status live in surprise. I will ask for status before I look at anything else.

A commit is not a save. Your editor already saved the bytes to disk. A commit is a checkpoint you are willing to talk about later. Good messages say why, not update.

Do this now

mkdir -p /tmp/c0-4 && cd /tmp/c0-4
git init
echo "C0.4 lab" > README.md
git status
git add README.md
git commit -m "Explain the lab in the README"
git log --oneline

status should go from untracked to clean. log should show one commit with your message.

Diff and a second commit

Change the README. git diff shows unstaged changes. git add, then git diff --staged shows what the next commit will contain. Commit again. git log should now tell a two-step story.

Do this now

cd /tmp/c0-4
echo "Second line." >> README.md
git diff
git add README.md
git commit -m "Add a second line to the README"
git log --oneline

Two commits. The messages should be readable by a stranger.

Branches

A branch is a movable pointer to a commit. You make a branch before you experiment so main stays a place you can return to.

git switch -c try-it creates and moves you. git switch main moves you back. The file you added on try-it is not on main until you merge. Merge waits for C4. Today you need create, switch, commit, look around.

Do this now

cd /tmp/c0-4
git switch -c try-it
echo extra > extra.txt
git add extra.txt
git commit -m "Try a second file on a branch"
git switch main
ls
git switch try-it
ls

On main, extra.txt is gone from the listing. On try-it, it is back. The file is in history, not deleted.

Ignore junk. Keep secrets out.

What Git is not: undo as a lifestyle, a substitute for backups, a place to put passwords. Once a secret is committed, assume it is burned. History keeps the bytes.

.gitignore lists names Git should not track. Editor swap files, __pycache__, .DS_Store, .env. Commit the ignore file on day one.

Do not push to GitHub until I say. Publishing is not the skill this lesson is for. History you can explain is.

Do this now

cd /tmp/c0-4
echo .DS_Store > .gitignore
touch .DS_Store
git status
git add .gitignore
git commit -m "Ignore macOS folder dust"

status should not list .DS_Store as a file to add. It should list .gitignore until you commit it.

Implement

Closed-resource terminal drills. No Bandit walkthrough. No solutions on this site.

  1. Install Git if needed, then git --version. In a new folder, git init. Create a README. status, add, commit. Change the README. diff. Commit again. log. Be ready to show me the log.
  2. Create a branch. Switch to it. Add a file. Commit. Switch back to the original branch. In the work log, without looking at notes, say where that new file went and how you would get it back.
  3. Add a .gitignore that excludes at least one real junk pattern on your Mac. Commit it. Prove with status that a junk file is untracked on purpose.
  4. Write commit messages that say why. I will reject initial commit plus a dump.
  5. Do not push to GitHub until I say. Do not commit a secret. Do not use git add . if you cannot name what it will include.
