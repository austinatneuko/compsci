TCP

C11 Computer Networking

Locked. Until Gate A. Systems depth and remaining CS wait until you can apply. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Explain TCP as reliable byte stream: handshake, seq/ack, window, congestion mention.
  • Contrast UDP: datagram, no built-in reliability.
  • Say why a “slow API” might be a window or a retransmit, not your JSON.
  • Do not implement TCP.

Teaching

TCP exists so applications can pretend the network is a pipe. It is not a pipe. Loss, reorder, delay. Sequence numbers and acks, handshake (three-way), teardown, a window that limits in-flight data, congestion control that slows you when the network is unhappy. You need the story to debug, not the RFC.

UDP is “send this datagram, good luck.” DNS often uses it (C11.4). Games and voice use it with their own repair. HTTP/3’s QUIC is a later footnote, not this week’s implementation.

Networking is how HTTP stops being magic. Layers, sockets, TCP, a short DNS and routing, HTTP as bytes, TLS as a job, a packet lab. You will write a small TCP client and server and explain a slow API with the network, not the framework. C-syslit was the seatbelt. This is the course. You will not become a network engineer. You will read a capture without drowning.

Handshake, sequence and ack, window, congestion as a story. Loss, reorder, delay. UDP is a datagram and good luck. DNS often uses it. HTTP/3 is a footnote, not this week's implementation. Explain a large download on a lossy link without saying the JSON is slow.

A capture is evidence. A slogan about the cloud is not. Client and server you wrote are evidence. Kurose and Ross selected, Wireshark labs I assign. Optional CS144 is depth, not an excuse to skip the small socket work. Explain slowness with hops and windows and loss, then maybe the handler.
