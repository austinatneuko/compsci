Specs and pre/post

C4 Software Construction

Locked. Because the prerequisite course is not mastered. You are on C0.1. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Write a spec with preconditions, postconditions, and an invariant you can test.
  • Separate what the function promises from how it is implemented.
  • Refuse a spec that is a restatement of the code.
  • Use the spec as the thing tests are allowed to check.

Teaching

A specification is a contract. If the caller meets the preconditions, the function meets the postconditions, and any invariant the type claims still holds. It is not a comment that repeats the for loop in English. A spec that repeats the loop in English is a diary. A spec another person could implement is a contract. MIT 6.1020's whole personality is this idea, and we steal it without stealing their Java. We do the work in Python.

Preconditions are what you assume. xs is non-empty. i is a valid index. The file exists. Preconditions are where you stop blaming the function. Postconditions are what is true after. The returned mean is the arithmetic mean. The list is sorted in nondecreasing order. The file now contains one extra line. Postconditions are what tests are allowed to see. Invariants are what stays true. This list has no duplicates. This stack's size is the number of pushes minus pops. Invariants are what must still be true after a public operation.

Why this is not ceremony: a test is a check of a contract. If there is no contract, the test is a snapshot of today's implementation. When I say write tests for a spec you did not implement on the C4 exam, I mean this skill. Black-box tests that could fail the spec even if they never see your body.

We will write specs before bodies on designated assignments. Where you write the body first, you will still go back and write the contract as if a stranger will implement against it. If the stranger could not, the spec is a diary entry. I will give you a spec with a hole. Find the hole. That is as useful as writing a clean one.

Take three C1 or C2 functions and write pre, post, invariant in a docstring format I specify. No AI on the first spec pass. A model will give you fluent restatements of the loop. That is the thing I am training you to refuse.

C4 is the course where other people have to live with your code. Specs, ADTs, tests, PR-quality Git, review, a debugging method, API-shaped errors, a little FP taste, and AI evaluation as law. MIT 6.1020 is the gold statement of the ideas; we do the work in Python. Google engineering practices are a baseline, not scripture. Dual-track work starts here: closed first, then catch the model. If you treat this course as a checklist of tools, you will still write a 400-line main. If you treat it as contracts plus history plus review, P1 becomes possible.

A spec that repeats the loop in English is a diary. A spec another person could implement is a contract. Preconditions are where you stop blaming the function. Postconditions are what tests are allowed to see. Invariants are what must still be true after a public operation. Write them before the body on the assignments I mark. The C4 exam will ask you to test a spec you did not implement.
