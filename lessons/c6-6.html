Objectives

  • Design a schema for a multi-table service: keys, nullability, a unique constraint.
  • Write a migration as a deliberate change, not as I edited prod by hand.
  • Name what happens to existing rows when you add a NOT NULL column.

Teaching

Schema design is where C6.3 meets a product. Users, sessions, items, orders, whatever the prompt is, get tables that can survive a month of use. You will over-normalize and I will tell you. You will under-normalize and I will tell you. The loop is the course. Sit in the rejection loop now. P1 will inherit this schema taste.

Nullability is a decision. Optional email is a nullable column or a missing row in a side table, not a silent empty string that means three things. Unique constraints are how you keep two users from owning the same username. Foreign keys are how you keep an order from pointing at a deleted user, or you define ON DELETE and mean it. Unique and foreign keys are how the database refuses a lie when the app has a bug.

Migrations: a file that takes the database from version N to N+1. We will use a simple tool I pick. You never just ALTER on a shared database without a record. Adding NOT NULL without a default on a table with rows is a failed migration waiting to happen. Think about the existing data. A migration is a versioned change that thinks about existing rows.

This design is load-bearing for P1. If you rush it, you will migrate in pain during the project. Add a column to a table that already has rows. Make the migration work. Closed-resource. No AI on the first design.

Every backend module ends in something I can run: a query, a migration, a curl, a test. Wandering docs is how people collect frameworks and still cannot explain a status code. Assigned pages only.

Backend work in this program is HTTP plus a relational database plus a thin framework, in that order. FastAPI is not the syllabus. If you cannot read a raw request, predict a join, or justify an index, a green OpenAPI page is decoration. We talk to Postgres with parameters before any ORM. Transactions are how two writes become one fact. Validation dies at the edge with a 4xx that names the field. The service you build here is the skeleton of P1. Dishonest schemas get rejected until they are honest. That loop is the course.

A migration is a versioned change that thinks about existing rows. Adding NOT NULL without a default on a full table is a failed deploy. Unique and foreign keys are how the database refuses a lie when the app has a bug. Sit in the rejection loop. P1 will inherit this schema taste.
