Sessions, cookies, JWT (and when JWT is a mistake)

C8 Auth, Quality, Delivery

Objectives

  • Implement sessions-in-cookies or a token scheme I approve, and defend it.
  • Know what a cookie's HttpOnly, Secure, SameSite are for.
  • Explain when JWT is a mistake: long-lived, unrevocable, stuffed with secrets.
  • Store passwords only as a slow hash. Never log them.

Teaching

A session is a server-side record. The browser holds an id. The server holds this id is user 19. A cookie is a header the browser keeps sending. HttpOnly means JavaScript cannot read it. XSS mitigation, not a cure. Secure means HTTPS only. SameSite is a CSRF lever. You will set these on purpose.

A session id in an HttpOnly Secure cookie is a design I can defend. JWT is a signed blob the client holds. It is useful when you truly need stateless verification across services you control. It is a mistake when you wanted a session: you cannot revoke easily, people stash permissions in the payload and never expire them, and a blog told them JWT is modern. A long-lived token stuffed with permissions and no revocation is a blog. We will implement one honest path. If we use JWT, we will put little in it and expire it.

Passwords: a slow hash, bcrypt or argon2, I pick. Never store plaintext. Never log the password. Reset flows wait until the basic login is not embarrassing. Passwords are a slow hash. Never log them.

I will try to steal a session the cheap ways: copy a cookie, hit without cookie. You will watch the logs. I will try the cheap thefts. You watch the logs.
