Objectives

  • Say, in your own words, what job a shell is doing, before you memorize anyone else's sentence.
  • Distinguish a graphical menu of actions from a textual interface that starts programs by name.
  • Know why engineers still type in a shell on machines that also have a desktop.

  • Leave Missing Semester lecture 1 closed until it is released in chat.

Teaching

You already know how to give a computer orders. You tap an icon. You click a menu. You ask a chat box to do something someone else wired up. Those screens are not the computer. A designer picked a short list of actions and put them where a thumb can reach. If the action is not on the list, you cannot name it. Fine for mail. Fine for maps. A ceiling if you want to engineer.

A working computer runs programs. Each program is a file. It takes input, does work, writes output, then exits. This lesson is not a Linux brand tour. I want you stuck on a blunter question. You need to start a program that is not on any menu, pass it arguments, read what it printed, and do that a hundred times, or do it on a machine you will never see. Tell me what kind of interface that is.

I will not hand you a one-line textbook definition and call you done. I want your sentence first. People who copy "a command-line interpreter" still freeze when a prompt sits there waiting. People who have a picture can learn the syntax later and not lose the plot. The picture I want is simple. A shell is a program whose job is to start other programs, pass them text, and show you what came back.

I still live in one on a laptop that has a perfectly good desktop. Text composes. The output of one program is text, and the next program will take text, so you can snap tools together that were never sold as a pair. Once you can name a sequence, you can put it in a file and run it tomorrow. The same textual interface works on your machine and on a server in another city that has no mouse and no screen. A GUI you cannot script, pipe, or SSH into is a local convenience. I will not accept that as your only environment.

A graphical installer hides a failure behind a spinner. A shell prints the error the program actually produced. Rude. Useful. You will read a lot of rude, useful text. I still do, most days, before coffee.

A session has a rhythm. It prints a prompt. You type a line. You press return. Something runs, or the shell tells you it could not find what you named. Then another prompt. At the user level that loop is the job. You are talking to a program that talks to other programs. Later we will be precise about processes, PATH, and exit codes. Today I want the shape. I do not want a glossary you can recite and then drop the moment a prompt looks different from the screenshot in a blog.

You may have used a "terminal" app. You have seen a black rectangle in a movie. The rectangle is a window. The program inside it is usually a shell. People mash those two into one word and then get lost when the window is fine and the program inside is stuck. We will split them in C0.3. For now, notice that the useful object is not the decoration. You name work. The machine does it, or it fails in public.

I will not mark C0.1 complete because you opened a webpage. I teach here. You answer in CompSci chat. You demonstrate on a real Unix shell, macOS Terminal, Linux, or Windows with WSL. A phone is for reading. The work happens on a computer that can run programs you type. If you only have a phone tonight, read and write the sentence. Do not pretend a phone prompt is this course.
