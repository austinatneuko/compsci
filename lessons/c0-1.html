Teaching

You already know how to give a computer orders. You tap an icon. You click a menu. You ask a chat box to do something that someone else wired up. Those interfaces are not the computer. They are a menu of actions a designer chose to put on the screen. If the action is not on the menu, you cannot name it. That is fine for mail and maps. It is a ceiling for engineering.

A working computer is a machine that runs programs. Each program is a file. It takes input, it does work, it writes output, it exits. The question this lesson is about is not “what is Linux.” It is: when you want to start a program that is not on any menu, pass it arguments, read what it printed, and do that a hundred times in a row or on a machine you will never see — what kind of interface is that?

I am not going to hand you a one-line textbook definition and call it mastery. I want your sentence first. People who copy “a command-line interpreter” can still be lost when a prompt is sitting there waiting. People who have a picture — a program whose job is to start other programs, pass them text, and show you what came back — can learn the syntax later and not lose the plot.

Why engineers use one, even on a laptop with a beautiful desktop: composition, repetition, and distance. Composition: the output of one program is text, and the input of the next program is text, so you can snap tools together that were never designed as a pair. Repetition: once you can name a sequence, you can put it in a file and run it tomorrow. Distance: the same textual interface works on your machine and on a server in another city that has no mouse and no screen. A GUI that cannot be scripted, piped, or SSHed is a local convenience. It is not a professional environment.

There is also honesty. A graphical installer will hide a failure behind a spinner. A shell prints the error the program actually produced. That is rude and useful. You will spend a career reading rude, useful text.

A shell session has a rhythm you will learn by ear. It prints a prompt. You type a line. You press return. Something runs, or the shell tells you it could not find what you named. Then another prompt. That loop is the whole game at the user level: you are talking to a program that talks to other programs. Later we will be precise about processes, PATH, and exit codes. Today I want the shape, not the glossary.

You may have used a “terminal” app, or seen a black rectangle in a movie. The rectangle is a window. The program inside it is usually a shell. People conflate the two. We will separate them in C0.3. For now, notice that the useful object is not the decoration. It is the conversation: you name work, the machine does it or fails in public.

This program will not mark C0.1 complete because you opened a webpage. I teach here. You answer in CompSci chat. You demonstrate on a real Unix shell — macOS Terminal, Linux, or Windows with WSL. A phone is for reading. The work happens on a computer that can run programs you type.
