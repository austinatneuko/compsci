Errors and exceptions

C1 Programming Fundamentals (Python)

Locked. Because C0 module 3 (editor and terminal workflow) is not mastered yet. C1 can start in parallel only after that. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Distinguish an error you should let crash from an error you should catch.
  • Raise a specific exception with a useful message when the caller violated a contract.
  • Write try / except / finally (or with) without a bare except:.
  • Read an exception type as information: TypeError, ValueError, KeyError, FileNotFoundError.
  • Stop swallowing errors to make a demo look clean.

Teaching

An exception is how Python says “this call did not complete the job.” It is not a moral failure. It is a value with a type and a message and a stack. Uncaught, it ends the program and prints a traceback. That is often the correct outcome. A program that cannot open its config should not pretend it did.

You raise when your function’s contract was broken: empty list where you required at least one item, a negative where you required a count, a key the caller claimed existed. Prefer specific types: ValueError for a bad value of an otherwise right type, TypeError for a wrong type if you must check types (usually you do not, in Python, unless the failure would be silent). KeyError and IndexError are already the right types for missing keys and bad indexes; you do not need to wrap them in a new poetry.

You catch when you have a plan. except FileNotFoundError and then create the file, or tell the user which path failed, is a plan. except Exception: and pass is how you ship a lying program. Bare except: also catches KeyboardInterrupt and SystemExit in ways you will regret. I will reject bare excepts.

finally runs whether or not the block succeeded. You need it for cleanup you cannot express with with. Prefer with for files and later for locks. else on try means “no exception,” and it is rare in this course; do not collect syntax.

EAFP versus LBYL: Python culture often says “easier to ask forgiveness than permission” — try the operation, catch the specific miss — versus “look before you leap” with if k in d. Both are legal. Racing checks and uses becomes a real bug in concurrent code (C10). For C1, pick one, be consistent, and do not check then immediately do something that can still fail without handling it.

Messages are for the next human, often you. raise ValueError("xs must be non-empty") is a sentence. raise ValueError("error") is noise. Include the offending value when it is not a secret and not a novel.

We still do not use exceptions for ordinary control flow (try to find the end of a list). Walk the list. Exceptions are for exceptional exits and for contracts.

A useful habit: when you catch, log or return enough for the next function to decide, then stop. When you raise, you are telling the caller the job did not happen. Those are different letters. Mixing them in one function is how C1 programs become C4 rewrites. We will keep the rule small this week and make it law in construction.

Work

Exercises are listed so you can see the shape of the work. They are not assigned. Do not start them. No solutions on this site.

  1. Revisit mean and the max-score function. Raise ValueError on empty with a message you would accept from a library.
  2. Write a function that opens a path and returns its text, and converts FileNotFoundError into a ValueError that includes the path. Catch only FileNotFoundError.
  3. I will give you a ten-line function with a bare except. Rewrite it. In chat, say what error it was hiding.
  4. Trigger KeyError, TypeError, and FileNotFoundError on purpose. Catch none of them. Read each type. Closed-resource.
  5. Do not use a model to “clean up” tracebacks. The traceback is the assignment.
