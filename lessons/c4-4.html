Objectives

  • Branch for a change. Write commits I would read on a team.
  • Explain merge vs rebase as history shapes, and when I want which.
  • Resolve a conflict on purpose without panic.
  • Use bisect as a search over history, not as folklore.

Teaching

C0.4 was local history. C4 is PR-quality Git. You work on a branch named for the change. Commits are a story a reviewer can skim. main is not your scratchpad. You will open pull requests against a course repo I maintain. The website is GitHub or equivalent. The skill is the history.

PR-quality Git is a story a reviewer can skim. Branch, commits that say why, a conflict you resolve without deleting the other side, bisect when last month is the only clue. Merge preserves the exact graph of what happened. Rebase replays your commits on a new base and rewrites history. Fine for your unpushed branch. Hostile on a shared branch. I will tell you which I want. I always rebase is not a personality I need. I understand both is.

A conflict is two edits to the same region. Git dumps both into the file and waits. You edit, mark it resolved, continue. You do not delete the other person's work because it is inconvenient. You do not commit conflict markers. I will create a conflict for you on purpose.

git bisect is binary search on commits. This one is bad, that one is good, Git picks the middle, you test. When a bug appeared sometime last month, bisect is the method. Random checkouts are not.
