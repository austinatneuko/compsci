Specify and build a command-line tool

P0 Command-line tool (project)

Locked. Because C0 is not mastered and C1 is not far enough along to specify a real tool. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Write a spec for a CLI tool that is not a tutorial clone.
  • Implement it in Python with tests and a README a stranger can run.
  • Use Git as the history of the work, not as a last-night dump.
  • Survive a code review and change what is rejected.

Teaching

P0 is the first thing in this program that is supposed to exist for a stranger. C1 proved you can write Python. P0 asks whether you can specify a job, cut it to a size you can finish, and leave a trail. The failure mode I see most is a weather-app clone from a blog with my name in the README. I will reject that on the spec, before you write a line of the body.

A command-line tool has a contract you can say out loud. It reads arguments or stdin. It writes stdout or files. It exits nonzero when it fails. It does not require a GUI. Pick a job you actually have. Rename a pile of files. Summarize a CSV you care about. Deal a practice quiz from a question file. Check that a directory tree matches a checklist. Small and real beats large and fake. If you pick a problem you do not care about, the spec will be fog and the tool will be a clone with the serial numbers filed off.

A spec I will accept names inputs, outputs, errors you will handle, errors you will refuse, and how I run it. That paragraph is a spec. A bullet list of verbs is a wish. I will reject wishes. Example of a decision: the tool reads a directory of UTF-8 notes and prints a count per tag, tags are hash-leading words, unknown flags are errors, and I will not crawl the network. After I accept, the implementation is C1.9 at project size. Parse at the edge. Decide in functions I can test. Print in main.

Git commits as you go. If the story of the work is one commit titled final, we redo the history even if the binary behaves. That is not busywork. That is how I know the next project will not be a dump. A README is a contract with a future stranger, often you in a month. One copy-paste command that runs the tests. If that command does not exist, the README is not done.

I review like a demanding mentor. What is wrong, why it matters, what a stronger engineer would have considered. You correct it with commits, not with a debate about taste unless I was factually wrong. Completing a first draft is not the exit. The loop is the work.

No AI on the first draft of the spec. If I later mark a pass AI-open, you still read every line. I will clone the repo and run it from a clean directory. I will try a wrong flag. I will read the log. A tool you specified is also a rehearsal for every later review.

P0 exists because C1 can produce a person who writes functions and still cannot ship a tool a stranger will run. A spec is a decision about who the user is and what failure looks like. A README is a contract with a future stranger, often you in a month. Git is the history of those decisions, not a zip file at the end. Review is how I refuse a tutorial clone before you spend a weekend on it. If you pick a problem you do not care about, the spec will be fog and the tool will be a clone with the serial numbers filed off. Pick a job you have. Cut it until a week of nights can finish it. Then we review.

The failure mode I see most is a spec that lists features instead of decisions. A decision looks like: the tool reads a directory of UTF-8 notes and prints a count per tag, tags are hash-leading words, unknown flags are errors, and I will not crawl the network. That paragraph is a spec. A bullet list of verbs is a wish. I will reject wishes. After I accept, the implementation is C1.9 at project size: parse at the edge, decide in functions I can test, print in main. If you cannot run the tests with one command, the README is not done.
