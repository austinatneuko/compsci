Testing a function

C1 Programming Fundamentals in Python

Locked. Because C0 module 3, editor and terminal workflow, is not mastered yet. C1 can start in parallel only after that. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Write a pytest function that calls your code and asserts a specific result.
  • Separate the example you printed while hacking from a test that will still be there Tuesday.
  • Cover an edge. Empty, one item, a tie, a missing file, whatever your docstring promised.
  • Run tests from the terminal and read a failure as a diagnosis.
  • Treat a test that cannot fail as not a test.

Teaching

A test is a program that checks another program. That sounds circular and is the whole job. You pick a concrete input, you know the output, or the error, that the contract demands, you call the function, you assert. If the function changes later and the contract does not, the test fails, and you just got a letter from last week's self.

We use pytest because it is the default in this program's Python path. A test file is named test_*.py or *_test.py. A test function is named test_*. Inside, assert a boolean. pytest rewrites the assert so a failure shows both sides. You do not need unittest's ceremony this month.

What to test. The examples in your docstring, then one edge the docstring mentioned, then one error path you raise. What not to test. The existence of a function, assert mean is not None. The ability of Python to add 1 and 1. The exact wording of a message you will change every hour. Do not assert on printed output if you can return a value. Returning is what made C1.3 load-bearing.

A test that cannot fail is not a test. assert True is a joke. A test that copies the implementation, assert mean(xs) == sum(xs)/len(xs) when the body is that line, is a tautology. It still has some value as a regression if the body changes, and none as a specification if you derived both from the same thought. Prefer independently computed fixtures. assert mean([2, 4, 6]) == 4.

Run pytest from the project directory. A failing test is a gift with a file and a line. You will not delete the test to make the suite green. You will not mark it skipped unless I say the contract changed. Green through deletion is a kind of fraud I can see in git diff.

This lesson is the start of a habit C4 will make law. You will not wait until the function is done to test. You will write the contract, a test that could fail, then the body. If that is too doctrinaire for a six-line function, write the body first and the test before you commit. The commit with the function and no test is the one I will send back.

Closed-resource. No model writing your tests. A model will assert the implementation and miss the empty list. That miss is the point of the lesson.

Work

Exercises are listed so you can see the shape of the work. They are not assigned. Do not start them. No solutions on this site.

  1. Install pytest if needed, pip in the environment I approved. Run pytest in a folder with one deliberate failing test so you see a failure. Then fix it.
  2. Add tests for mean, word count, and one file function. Include empty-or-missing paths you promised in docstrings.
  3. Write one test that you expect to raise, pytest.raises. Point it at a real contract, not at 1/0.
  4. Commit tests in the same repo as the code. pytest must be the command I run.
  5. Closed-resource. No AI. Weekly quiz includes what does this failure say.
