Objectives

  • Validate input at the edge. Reject bad JSON with a 4xx that names the field.
  • Do not trust the client: types, ranges, unknown fields.
  • Keep 5xx for your bugs, not for user forgot email.
  • Log the error id, not the user's password.

Teaching

Validation is part of the API contract. FastAPI and Pydantic will do a lot if you let types tell the truth. A string email field that accepts empty is a lie. An integer age that accepts -3 is a lie. Extra fields: reject or ignore, but decide. Bad JSON is a 4xx that names the field.

Error bodies stay consistent with C6.2. 422 vs 400. We will pick a convention and keep it. Do not return a stack trace to the client. A stack trace is not an error body. Do not return 500 because int(request) failed. That is a 400. 500 is yours.

Auth errors wait for C8, but you will already return 401/403 as placeholders in the right places rather than 404-to-hide, unless we decide to hide existence on purpose. We will say so. Do not use 404 as a blanket hide unless we said so.

Tests include a bad body. If your suite only sends happy JSON, you have not tested the API. I will send bodies that should 4xx. Closed-resource. No AI.

Add validation to the C6.8 service. Tests for missing field, wrong type, and one range. If the suite only sends happy JSON, you have not tested the API.

Backend work in this program is HTTP plus a relational database plus a thin framework, in that order. FastAPI is not the syllabus. If you cannot read a raw request, predict a join, or justify an index, a green OpenAPI page is decoration. We talk to Postgres with parameters before any ORM. Transactions are how two writes become one fact. Validation dies at the edge with a 4xx that names the field. The service you build here is the skeleton of P1. Dishonest schemas get rejected until they are honest. That loop is the course.
