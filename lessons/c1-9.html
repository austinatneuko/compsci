Decomposition

C1 Programming Fundamentals (Python)

Locked. Because C0 module 3 (editor and terminal workflow) is not mastered yet. C1 can start in parallel only after that. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Take a fuzzy 80-line idea and split it into functions with names that are jobs.
  • Keep I/O at the edges: read in one place, decide in another, write in a third.
  • Name data: if a tuple is really a record, say what the fields are.
  • Delete the leftover comments that narrate i += 1 and keep the ones that say why.
  • Use Git commits as the history of the split, not one dump at the end.

Teaching

Decomposition is the skill of turning “the program” into pieces you can hold. It is not an aesthetic of many tiny files. It is the ability to say: this function decides, this one parses, this one formats, this one is the process you would name to a person. C1.10 will ask you to design an 80–150 line program. This lesson is the rehearsal.

A useful split follows jobs, not language features. “All the lists” is not a job. “Parse a line into a record” is. “Decide whether the record counts” is. “Format a report line” is. When a function does two jobs, you will feel it in the name: parse_and_write, check_and_update_and_log. That name is a confession. Split.

I/O at the edges. If the function that decides also opens files and prints, you cannot test the decision without the filesystem and a human eyeball. Return data. Let main read argv, open files, print. This is the same sermon as return-versus-print, now at program scale.

Names are design. data2 means you have not designed. rows is better. payments is better than rows if they are payments. If you need a comment to explain a name, the name lost. If you need a comment to explain a trick, keep the comment and consider deleting the trick.

Dead code is a kind of undeclared debt. Functions you wrote, stopped calling, and left “just in case” are how a homework becomes a junk drawer. Git already keeps the past. Delete from the present.

Work incrementally. The first running program may be a single file with three functions and a main. The second commit extracts a helper. The third adds tests for the helper. I will look at the log. A single commit titled “final” after two silent weeks is a story I do not believe and cannot review.

A test for the split: if I delete one function, can you describe the hole in one noun phrase? If the hole is a pile of leftover jobs, the seams are fake. If the hole is parse, or report, or decide, you are done enough to start C1.10.

If I ask you to trace the program on paper, I should be able to stay inside one function at a time. That is the practical meaning of a seam. C1.10 will not give you a new construct. It will ask whether these seams hold at 80 to 150 lines.

You will feel slower. That is the lesson costing what it costs. Speed without seams is how people write the 400-line main they cannot debug on the C1 exam.

Work

Exercises are listed so you can see the shape of the work. They are not assigned. Do not start them. No solutions on this site.

  1. Take one of your C1 homework programs that is getting long. Split it until every function is explainable in one sentence. Tests still pass.
  2. Write main so that the decision functions do not call print or open. If they need text, they take a string or a list of lines.
  3. In chat, list the functions and their one-sentence jobs. I will tell you which names are still two jobs.
  4. Commit at least three times during the split, with messages that say what changed.
  5. Closed-resource. No AI rewrite of the whole file. You may not paste the program into a model and ask it to “clean this up.”
