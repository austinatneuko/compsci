C10 Operating Systems and Concurrency

Locked. Until Gate A. Systems depth and remaining CS wait until you can apply. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Define a thread as a schedulable stack inside a process.
  • Share memory on purpose; say what is shared vs not.
  • Write one threaded program that is wrong, then say why.
  • Do not “just add threads” for speed without a story.

Teaching

Threads share the heap and globals; each has a stack and registers. That is why they are cheap to communicate and expensive to get right. Processes share nothing by default (except what you ask for). C-syslit mentioned this; now you will write it.

A data race is undefined in C’s memory model and a bug in every language. You will produce one (a counter++) and watch it lose increments. Then C10.5.

Python’s GIL is a footnote: threads may not speed CPU-bound Python. That does not make races impossible (I/O, C extensions). Do not hide in the GIL as a moral.

OS and concurrency is processes, virtual memory, files, threads, locks, deadlock, a short scheduler, and one real artifact. OSTEP is the text. xv6 or a user-level thread package or a tiny filesystem — I designate one, not the whole MIT course. The exit is a concurrent bug you can fix with a named invariant, and a read you can explain. Just add a lock is a sentence we will kill with an example.

Shared heap, private stacks. Produce a racy counter and watch lost increments. The GIL is a footnote, not a moral. Do not add threads for speed without a story. What is shared is the written question.

Concurrency bugs are not fixed by hoping. Name the invariant. Name the missing one. Change one thing. The artifact is there so you lived in the basement, not so you can sticker a portfolio. OSTEP homeworks are assigned chapters, not the whole book in a weekend. I designate the build so we finish.
