Errors and API shape

C4 Software Construction

Locked. Because the prerequisite course is not mastered. You are on C0.1. You may read so the catalog is a real map. Do not start the exercises or the assigned reading until this lesson is current. Ratings do not move from a URL.

Objectives

  • Shape an error so the caller can do something.
  • Pick a return vs raise policy and keep it inside one ADT.
  • Do not leak internal exceptions as the public API.
  • Write error messages that include the useful noun: path, key, id.

Teaching

API shape is not only URL paths. Those are C6. It is how any module talks to its caller when the job fails. Raise vs return-None is a decision. Mixing them is how callers sprout if result is not None next to a try/except they copied. Error policy is part of the ADT. Raise or return, not both at random.

Public errors should be the contract. KeyError if you are a mapping. ValueError if the value is illegal. A small custom type if you have a real domain. Catching Exception and re-raising Exception("error") is how information dies. Chain if you wrap, raise X from e, so the traceback still teaches. Wrapping every exception as a generic failure is how information dies.

Messages get the useful noun. FileNotFoundError: config.toml is useful. something went wrong is a shrug. Do not dump secrets into errors. Do not dump 200 lines of HTML.

We will look at a few standard-library functions and say what they promised. Then you will reshape a messy module I give you until a caller can handle failures without reading your source. A caller who must read your source to handle a miss is using an unofficial API. Reshape until they do not have to.

Closed-resource: given a spec, write only the errors and the signatures, not the bodies. Find one leaked internal exception in a snippet I paste. Name the leak. No AI on the first reshape.

C4 is the course where other people have to live with your code. Specs, ADTs, tests, PR-quality Git, review, a debugging method, API-shaped errors, a little FP taste, and AI evaluation as law. MIT 6.1020 is the gold statement of the ideas; we do the work in Python. Google engineering practices are a baseline, not scripture. Dual-track work starts here: closed first, then catch the model. If you treat this course as a checklist of tools, you will still write a 400-line main. If you treat it as contracts plus history plus review, P1 becomes possible.
